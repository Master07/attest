# Generated benchmark: 102 pre-registered planted-bug scenarios

> **Audience:** judges + devs · **Status:** final for runs 1 and 2 · **Last updated:** 2026-11-02 · **Related:** [pre-registration, run 1](../examples/bench-gen/PREREGISTRATION.md) · [pre-registration, run 2](../examples/bench-gen-r2/PREREGISTRATION.md) · [BENCHMARK (10 hand-written bugs)](BENCHMARK.md) · [receipts](../proofs/bench-gen/)

**Generated planted bugs, not real-world accuracy.** A deterministic generator built five small apps with about twenty planted UI bugs each, every one with a real fix and a plausible wrong fix. Everything was frozen and checked without AI before any model saw it, then each scenario ran once, live. Every result is below, including every INCONCLUSIVE with its reason.

## Headline

| | Run 1 (all 102) | Run 2 (checkout only, one change) |
|---|---|---|
| PROVEN | **55** | **17** of 19 |
| INCONCLUSIVE | 47 | 2 |
| REJECTED (real fix failed) | **0** | **0** |
| Wrong fixes certified | **0** | **0** |

- **No real fix was rejected:** Green never failed in 121 live runs.
- **No wrong fix was certified.** In 12 scenarios of run 1 a wrong fix passed its phase; all 12 ended INCONCLUSIVE, because another phase or voter disagreed. Disagreement is never a pass.
- **The baseline: every wrong fix came with a passing check.** 47 came with a behavioural unit test that passes, and 55 with a source check (on the CSS or HTML) that passes. A source check is not a behavioural test, so the baseline row counts only the 47: **tests alone would have accepted 47 of 47 wrong fixes; Attest certified 0 of them** (it rejected 37 outright in Break; the other 10 ended INCONCLUSIVE).
- **The weak spot is layout bugs:** controls clipped, pushed off-screen, invisible or zero-sized. Only 3 of 25 were PROVEN. Attest mostly refused to certify them rather than passing a wrong fix.
- **One of the causes was our mistake.** The checkout app showed a quantity of 9 while its frozen criterion said "a cart with one item". The judge rightly refused to pass those pages. Run 2 changed only that value and re-ran checkout: 8 → 17 PROVEN.

## How it was run

- **Scenarios:** 5 app shells (checkout, search, settings, signup, todo) × 21 bug recipes, generated by `scripts/gen-bench.ts` (deterministic). 103 generated; the AI-free check dropped `G-signup-strict-pattern` (its wrong-fix test failed), leaving **102**. Two combinations were never generated ([SKIPPED.md](../examples/bench-gen/SKIPPED.md)).
- **Frozen first:** shells, criteria, recipes and scenarios were committed and the [pre-registration](../examples/bench-gen/PREREGISTRATION.md) written before any model run. Every run's `criteria_sha256` matches the committed criteria file (checked for all 121 runs).
- **AI-free check before the run:** for each scenario, the base must fail a scripted probe, the fix must pass it, and the wrong fix's own test must pass.
- **Voters:** Muse Spark 1.3 (blind computer-use verifier), deterministic code checks, and the Muse Spark Open judge (open weights, Baseten). SAM 3.1 had nothing to check in these criteria and abstained everywhere. Step cap 25 per phase. Video off (`ATTEST_VIDEO=0`); screenshots, logs and signed receipts kept.
- **Once each, sequentially:** run 1 from 2026-11-01 11:48 to 22:59 UTC; run 2 on 2026-11-02 from 01:05 to 02:13 UTC. No Meta API 5xx occurred, so nothing was re-run. Neither run stopped early.
- **Overlap to note:** while run 1 was on `G-search-delayed-enable` (14:02–14:10 UTC) and `G-search-double-apply` (14:10–14:30 UTC), other exploratory Attest runs were executing on the same machine. Both are reported as they came: delayed-enable PROVEN, double-apply INCONCLUSIVE.

Each INCONCLUSIVE is put in one group, checked in this order:

| Group | Count | What happened |
|---|---|---|
| **A. Our checkout contradiction** | 10 | Green: the verifier and the code checks passed, the judge failed. The page showed quantity 9 against a criterion saying one item, and the judge was right. Run 2 fixed the value: 9 of the 10 ran again and all 9 were PROVEN; the 10th was dropped as pre-registered. |
| **B. Bug not reproduced, or the wrong fix passed** | 12 | In 9 the bug didn't show on the base build; in 11 a wrong fix passed Break (8 had both). Mostly layout bugs: a control that is off-screen, invisible, zero-size or clipped. The verifier can reach it in ways a user can't, for example by scrolling or using the keyboard. |
| **C. Step cap hit** | 9 | The verifier used all 25 steps without a verdict in at least one phase, mostly on fixed-banner, clipped and off-screen controls it kept hunting for. |

The check's probe clicks the centre of the control, so a bug that only affects part of it gets past the probe while the models see it. In the rest, the verifier and the judge disagreed. |

## What the numbers mean, and what they don't

- They show the mechanism on generated bugs: no real fix rejected, no wrong fix certified, and an honest INCONCLUSIVE where Attest can't tell.
- They are **not** a measure of real-world accuracy, and they are only as broad as the 21 recipes.
- Several INCONCLUSIVEs come from the benchmark, not from the app: our checkout contradiction, and code-check probes that click only the centre of a control. Both are reported as they happened, not repaired.
- The layout weakness is real. A verifier that can scroll or use the keyboard can reach controls a mouse user can't. That makes the bug hard to reproduce, and Attest then refuses to certify.

## Reproduce

```bash
npm run gen-bench                                                  # deterministic; regenerates examples/bench-gen
npm run bench -- build --root examples/bench-gen --prefix bench-gen
npm run bench -- check --root examples/bench-gen --prefix bench-gen  # AI-free; no key needed
ATTEST_VIDEO=0 npm run bench -- run --root examples/bench-gen --prefix bench-gen --ids <ids>   # live, needs keys
npm run verify-proofs                                              # checks every committed receipt, no key
```

The receipts are in [proofs/bench-gen/run-1](../proofs/bench-gen/run-1/) and [run-2](../proofs/bench-gen/run-2/). Their `results.md` and `results.json` are the benchmark script's original output (unsigned; the `receipt` paths in them point to the original `evidence/` folders). Each scenario folder holds a signed receipt, the event log, screenshots and an evidence page.
